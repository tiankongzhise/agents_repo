# AGENTS 同步规则库 PRD

## 项目目标

维护跨项目复用的 `AGENTS.md` 通用协作约束，并提供 `agents-md-sync` skill，帮助项目在本地同步中央规则后，只把项目根目录给 AI 读取的 `AGENTS.md` 发布回中央仓库供人工审查和公共规则提炼。

## 用户角色

- 项目维护者：希望各项目共享通用 AI 协作规则，并能审查项目回传的规则差异。
- AI 助手或自动化代理：在项目初始化、文档更新、bug 修复和功能开发前执行规则同步。

## 当前需求

### 核心文档颗粒度标准

中央规则需要明确 `docs/PRD.md`、`docs/DESIGN.md`、`docs/TECH.md`、`docs/SPEC.md`、`docs/DEVELOPMENT_PLAN.md` 和 `AGENTS.md` 的职责边界与最低详细程度。目标是在不制造冗长模板负担的前提下，让项目文档达到可实现、可验证、可交接的程度，并参考 skill 文档中“按任务脆弱度设置自由度、保持上下文精简、把详细参考按需拆分”的惯例。

#### 用户价值

- 项目维护者可以用统一标准审查文档是否足以支撑开发。
- AI 助手或自动化代理能判断新增需求应该更新哪些文档，以及每份文档要写到哪一层。
- 后续开发者可以从文档追溯需求、设计、技术方案、规格和执行状态。

#### 范围内

- 在中央 `AGENTS.md` 中补充五类核心文档和 `AGENTS.md` 的最小充分颗粒度。
- 补充本仓库 PRD、DESIGN、TECH、SPEC 和 DEVELOPMENT_PLAN，说明该规则本身的需求、设计、技术影响、功能规格和完成状态。
- 明确无前端、无运行时代码、无部署迁移影响。

#### 范围外

- 不引入强制的长篇模板或固定标题顺序。
- 不要求所有项目补写历史缺失文档；仅要求后续新增或变更需求按标准维护。
- 不修改 `agents-md-sync` 的同步算法或命令模板。

### 显式发布授权

安装或首次使用 `agents-md-sync` 时，必须明确询问用户是否授权将本项目 `AGENTS.md` 推送到中央规则仓库。用户授权后，授权状态需要固化到目标项目的 `.agents-sync.json` 中，后续发布前先校验该授权，避免运行时推送审批被自动拒绝后导致本地 `AGENTS.md` 无法被中央仓库接收。

### 发布分支命名防冲突

`agents-md-sync` 发布回中央仓库时，不能只使用仓库名作为分支名。不同 GitHub owner 下可能存在同名仓库，例如 `owner-a/project` 和 `owner-b/project`，裸仓库名会把两个项目的 `AGENTS.md` 汇入同一中央分支。发布分支必须使用当前项目 GitHub 完整名 `owner/repo`，并在无法解析 owner 时停止发布、要求用户确认。

### 发布内容收敛

`agents-md-sync` 发布回中央仓库的内容必须严格收敛为目标项目根目录给 AI 读取的 `AGENTS.md`。中央项目分支只用于让维护者审查项目 AI 规则并提炼公共 `AGENTS.md`，不是项目镜像、备份或分发渠道。不得把目标项目的 `docs/`、`skills/`、源码、配置、同步报告、构建产物或其他文件推送到中央仓库项目分支。

### Codex 沙箱中的 GitHub CLI 误判

Codex 沙箱内执行 `gh auth status`、`gh repo view` 或 `gh api` 时，可能因为沙箱无法访问凭据、keychain、网络或配置而返回类似“无权限”或“未授权”的错误。该情况不应直接判断为 GitHub CLI 授权失效，也不应据此撤销或要求重做项目发布授权；应先按沙箱限制处理，必要时提权重试同一条 `gh` 命令。

## 核心流程

1. 读取目标项目本地配置和 `AGENTS.md`。
2. 从中央仓库获取最新通用规则。
3. 只把通用、适用且不冲突的规则写入本地 managed block。
4. 写入同步报告。
5. 当本地 `AGENTS.md` 发生变化且发布启用时，先检查项目内发布授权。
6. 如无授权，向用户索要明确授权；授权后写入 `.agents-sync.json`。
7. 将本地根目录 AI-facing `AGENTS.md` 作为唯一文件推送到中央仓库中以项目 GitHub 完整名 `owner/repo` 命名的分支。

## 约束

- 授权记录不得包含 token、SSH key、密码或任何凭据。
- 授权范围必须限定为将当前项目 `AGENTS.md` 推送到配置的中央仓库。
- 缺少授权、授权字段不匹配或用户拒绝授权时，不得执行发布。
- 发布内容必须只包含目标项目根目录 AI-facing `AGENTS.md`，不得包含项目其他文件。
- Codex 沙箱导致的 `gh` 权限类报错必须先按沙箱限制处理，不能误判为真实 GitHub 授权失效。
- 文档颗粒度规则必须适合跨项目复用，不能绑定本仓库的私有路径以外的特定业务域。
- 文档颗粒度规则应强调“足以交接和验证”，避免鼓励机械填充或过度文档化。
- 本需求无前端界面影响。

## 验收标准

- `AGENTS.md` 明确 PRD、DESIGN、TECH、SPEC、DEVELOPMENT_PLAN 和 AGENTS 的职责边界与最低详细程度。
- 文档规则说明可追溯、可实现、可测试、可交接的判断标准。
- 本仓库补齐 `docs/DESIGN.md`，并同步更新 PRD、TECH、SPEC 和 DEVELOPMENT_PLAN。
- 本次文档颗粒度变更不影响运行时、命令模板、同步发布授权流程或前端界面。
- `agents-md-sync` 文档明确说明安装或首次使用时需要索取发布授权。
- 默认 `.agents-sync.json` 配置包含 `publish_authorization` 结构且默认未授权。
- 发布流程明确要求校验 `publish_authorization.granted: true` 和授权范围匹配。
- 命令模板包含写入和校验授权的示例。
- 发布分支命名规则使用当前项目 GitHub 完整名 `owner/repo`，例如 `tiankongzhise/auto_backup_bdnetdesk`。
- 如果无法从 `gh` 或 `origin` 解析 owner，发布流程必须停止，不能退回到只使用仓库名。
- 发布流程和命令模板明确只提交中央临时仓库中的 `AGENTS.md`，并在发现其他路径时中止。
- `gh` 在 Codex 沙箱内出现权限类失败时，流程明确要求先提权重试同一命令，再判断是否需要 fallback 或人工处理。
