# 功能规格

## 核心文档颗粒度标准

### 背景

中央规则已经要求默认维护 PRD、DESIGN、TECH、SPEC、AGENTS 和 DEVELOPMENT_PLAN，但缺少每份文档应详细到什么程度的判断标准。结果容易出现两类问题：文档过粗，无法指导实现和验收；或文档过细，重复代码和制造维护成本。

### 规格

- `AGENTS.md` 必须声明核心项目文档遵循“最少充分、可验证、可交接”的原则。
- `PRD` 的最低颗粒度必须覆盖用户目标、用户角色、场景、范围、功能需求、非功能约束、验收标准、依赖、风险、待确认问题和 deferred 项。
- `DESIGN` 的最低颗粒度必须覆盖体验目标、信息架构、流程、页面/组件或交互状态，以及空、错、加载、权限、可访问性和视觉约束；无前端影响时写明无影响。
- `TECH` 的最低颗粒度必须覆盖架构决策、模块边界、数据模型、接口契约、外部依赖、配置环境、迁移部署、安全隐私、性能、观测日志、失败处理、官方依据和关键取舍。
- `SPEC` 的最低颗粒度必须覆盖输入输出、状态流转、校验规则、错误处理、权限、边界条件、数据字段、接口或事件契约，并追溯 PRD 条目。
- `DEVELOPMENT_PLAN` 的最低颗粒度必须覆盖任务拆分、顺序、依赖、影响文件或模块、执行者、状态、验证命令、测试覆盖、文档更新、阻塞点和 deferred 后续项。
- `AGENTS.md` 的职责必须限定为可复用协作约束、项目惯例、命令、环境坑点和安全边界，避免承载一次性产品需求或临时计划。

### 验证规则

- 每个 PRD 有效需求必须能在 SPEC 或 DEVELOPMENT_PLAN 中找到对应实现项，或明确标记为 deferred。
- 任一新增需求如果对设计、技术或 AI 协作约束无影响，必须在 SPEC 或 DEVELOPMENT_PLAN 中说明无影响及原因。
- 更新任一核心文档后，必须检查其他相关文档是否存在矛盾或漏项。

### 无影响说明

- 本规则本身不新增运行时代码依赖、UI、API、数据迁移或部署影响。

## AGENTS 同步授权优化

### 背景

原同步流程只通过 `auto_publish_on_agents_change` 判断是否发布，但该字段更像功能开关，不足以证明用户已授权当前项目把 `AGENTS.md` 推送到中央仓库。运行时推送命令仍可能因为审批策略被拒绝，导致中央仓库无法接收本地规则更新。

### 规格

- 新增项目内发布授权字段 `publish_authorization`。
- 安装、初始化或首次使用 `agents-md-sync` 时，如目标项目没有有效授权，必须显式询问用户是否授权发布。
- 用户授权后，写入 `.agents-sync.json`，并保留已有配置字段。
- 发布前必须校验授权字段；授权缺失、不匹配或已撤销时跳过发布。
- 推送命令如仍需运行时审批，审批说明必须包含已存在的项目内授权、中央仓库和目标分支。

### 无影响说明

- 本授权优化不新增运行时代码依赖。
- 本授权优化无 UI、API、数据迁移或部署影响。

## 发布分支命名防冲突

### 背景

原 `agents-md-sync` 规则把中央仓库发布分支定义为“当前 GitHub 仓库名”，例如 `auto_backup_bdnetdesk`。该规则无法区分不同 owner 下的同名仓库，可能导致多个项目写入同一中央分支。

### 规格

- 发布分支必须使用当前项目 GitHub 完整名 `owner/repo`，例如 `tiankongzhise/auto_backup_bdnetdesk`。
- 解析仓库信息时优先使用 `gh repo view --json nameWithOwner --jq .nameWithOwner`。
- 无法使用 `gh` 时，必须从 `git remote get-url origin` 解析 GitHub owner 和 repo。
- owner 和 repo 必须分段清洗：转小写，只保留字母、数字、`.`、`_`、`-`，其他字符替换为 `-`。
- 清洗后用 `/` 拼接 owner 和 repo，保留该斜杠作为中央分支命名空间分隔符。
- 如果无法解析 owner 或 repo，发布流程必须停止并要求用户确认完整 `owner/repo`；不得退回到只使用 repo 名。
- 命令模板必须统一使用 `publishBranch` 或 `publish_branch` 作为推送分支变量，避免和裸 `repoName` 混用。

### 无影响说明

- 本变更不修改同步授权字段、中央仓库地址、中央主分支或本地 managed block 规则。
- 本变更不新增运行时代码依赖、UI、API、数据迁移或部署影响。

## 发布内容收敛

### 背景

`agents-md-sync` 的回传目标是让维护者从项目根目录 `AGENTS.md` 中提炼可复用公共规则。若中央项目分支继承中央仓库主分支内容，或发布流程复制目标项目目录，就会把 `docs/`、`skills/` 等无关文件带到中央仓库项目分支，违背“只审查项目 AI 规则”的本意。

### 规格

- 发布源文件必须是目标项目根目录给 AI 读取的 `AGENTS.md`，或配置为根级文件名的大小写变体。
- 发布到中央仓库项目分支的目标路径必须是 `AGENTS.md`。
- 中央项目分支必须只包含单个 `AGENTS.md` 文件。
- 发布流程不得复制目标项目目录、`docs/`、`skills/`、源码、配置、同步报告、构建产物或其他路径。
- 发布模板不得使用 `git add .`；必须显式暂存 `AGENTS.md`。
- 发布前必须检查中央临时仓库 `git status --porcelain`，发现任何非 `AGENTS.md` 路径时立即中止并报告路径。
- 远端项目分支已有相同 `AGENTS.md` 时，应跳过 commit 和 push。

### 无影响说明

- 本变更不改变中央主分支公共 `AGENTS.md` 的合并策略。
- 本变更不新增运行时代码依赖、UI、API、数据迁移或部署影响。

## Codex 沙箱中的 GitHub CLI 误判

### 背景

Codex 沙箱内的 `gh auth status`、`gh repo view` 或 `gh api` 可能因为无法访问本机凭据、keychain、配置目录或网络而显示类似“无权限”“未授权”的错误。这类错误常常是沙箱限制，不代表 GitHub CLI 真实未登录，也不代表项目 `.agents-sync.json` 中的发布授权失效。

### 规格

- 执行 `gh auth status`、`gh repo view` 或 `gh api` 失败且错误表现为权限、认证、凭据、网络或配置访问问题时，必须先标记为可能的沙箱限制。
- 对解决当前任务必要的 `gh` 命令，应按 Codex escalation 规则提权重试同一命令。
- 只有提权后仍失败，或错误信息明确指向真实 GitHub 授权、仓库权限或 token 问题时，才能判断为 GitHub CLI 授权问题。
- 不得因为沙箱内 `gh` 权限类失败而撤销、忽略或重写 `.agents-sync.json` 中的 `publish_authorization`。
- 若无法提权或提权后仍失败，应 fallback 到 plain Git 能力；仍无法完成时报告具体命令和失败原因。

### 无影响说明

- 本变更不改变发布授权字段结构。
- 本变更不新增运行时代码依赖、UI、API、数据迁移或部署影响。
